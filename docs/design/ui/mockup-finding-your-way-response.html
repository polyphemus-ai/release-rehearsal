Finding your way — a response

Answers the six journeys in finding-your-way-brief.md. Four decisions do the work: group, don’t sort; opening a project scopes Home rather than replacing it; the list never reorders under you; and a mark is never a model. The project page gets two tabs, not three. Everything here is on the app’s tokens, light and dark, at 400px and 1200px.

Groups are ordered by their newest thread, so the busy project is still on top. Waiting on you sits above all of them, ungrouped.

Group, don’t sort

“Sort by project” alphabetises and destroys recency. Grouping keeps newest-first inside each project and promotes the project name from grey text on line two to a heading with its colour.

Three options only

Time · Project · Agent. Time is the default and the one the settled brief describes. Nothing else earns a slot.

No project, no agent

Grouped by project, threads with none fall into a “No project” group, last. Grouped by agent, a thread files under its lead agent, or its only agent, or “No agent”. A thread never appears twice.

Groups collapse

Tapping a group heading collapses it, and that’s remembered. Collapsing hides rows, so a collapsed heading always shows its count.

At 400px the project replaces the thread, so a return bar carries the way back. It names the thread — not “back”.

The list never reorders under you

New and updated threads collect into a “3 new” pill instead of pushing the row you’re reading down the list. Anything waiting on you ignores the pill and arrives immediately, because that’s the one thing worth interrupting for.

Tool names collapse

A grant shows a count, then the tools that change things, then “+5 more”. Three GitHub identities cost three cards, not three screens.

Say when it takes effect

Every grant change states its scope in time: next turn, not retroactive, and never silently applied to a gate already waiting.

Two tabs, not three

Work and Conversations were one list split in two. Merging them removes the “which list is this thread in?” question that §2 exists to prevent.

Journey 4. Grouping changes the rows below, never the cards above. Each card names its project, since the heading that would have said it is now further down.

The one place I think §4 is under-specified: “Waiting on you stays on top, however the list is arranged” is enough for grouping, which hides nothing, but not for filtering, which does. A gate in another project sitting silently behind a filter is the worst failure this screen can have. So: a filter never hides a waiting item without a line saying how many and where, and that line clears the filter in one tap.

Two roll-ups stand in for ten rows. A roll-up never spans projects silently — its mark stacks the projects it covers and its line two names them.

A mark is never a model

Today a thread with no agent borrows its model’s mark, so most rows lead with the same orange hexagon. The mark slot answers “whose is this”: an agent’s mark, or a person’s face, or the project’s squircle, or a dashed outline if it has none. Models aren’t identities and never appear in the slot.

Roll-up rules

Three or more consecutive threads, all started by polyphemus, all quiet, all the same kind. Opening one expands it in place. Anything waiting on a person breaks the run and shows as its own row.

Started-by is on line two

“polyphemus · …” or “you started this”. It’s prose, not a fourth signal, so the three-signal rule holds.

No project stripe

I considered a coloured edge on each row for its project. It reads as a fourth signal and fights the amber dot. The project’s colour already arrives via the group heading, the filter chip, or the squircle when there’s no agent.

Setup’s icon. Sliders: two horizontal tracks with a knob on each. It reads as settings at 19px, it doesn’t collide with Team’s two people, and it isn’t the gear that every other app uses for a menu you close immediately.
